2. Descrição Resumida do Sistema

O sistema analisado é um protótipo web para registro de ocorrências acadêmicas em uma instituição de ensino. Sua finalidade é permitir o registro, a consulta e a exportação de eventos relacionados a alunos, como ocorrências disciplinares, acadêmicas, de saúde, administrativas e familiares.

O sistema apresenta as seguintes funcionalidades principais:

  • Tela de login com usuário e senha;
  • Cadastro de ocorrências com dados do aluno (nome, CPF, matrícula, turma, tipo, descrição e gravidade);
  • Listagem de ocorrências registradas;
  • Visualização de perfis de usuário;
  • Área de logs de ações;
  • Exportação de dados nos formatos JSON e CSV.

O sistema prevê três perfis de usuário: administrador, professor e aluno. Entretanto, na versão original, as diferenças entre esses perfis não são enforçadas de forma real.

⚠️ Importante: O sistema não possui back-end, API ou banco de dados real. Toda a lógica de negócio, autenticação, armazenamento e controle de acesso ocorre exclusivamente no navegador do usuário (front-end), utilizando JavaScript e localStorage.

3. Regras de Negócio Percebidas

A partir da análise do código-fonte, identificaram-se as seguintes regras de negócio simuladas no protótipo:

  • Somente usuários com credenciais válidas (verificadas no front-end) podem acessar o sistema;
  • Qualquer perfil autenticado pode cadastrar, visualizar e exportar ocorrências — não há separação real de permissões;
  • Professores e administradores deveriam ter acesso amplo; alunos deveriam ver apenas suas próprias ocorrências;
  • A área de logs deveria ser restrita a administradores;
  • A exportação de dados deveria ser restrita a administradores e professores;
  • Ocorrências de gravidade crítica recebem destaque visual diferenciado;
  • Ações como login, logout e cadastro são registradas em log — porém apenas no localStorage.

Todas essas regras estão implementadas exclusivamente no JavaScript do front-end, o que significa que qualquer usuário com conhecimento técnico pode inspecioná-las, modificá-las ou contorná-las pelo console do navegador.

9. Justificativa Técnica das Decisões

Item 1 — Credenciais hardcoded

Problema: As senhas de todos os usuários estavam em texto puro no array usuarios no JavaScript. Como qualquer arquivo JS é acessível via DevTools, qualquer visitante pode ver todas as credenciais.

Risco: Violação total de confidencialidade. Conceito relacionado: exposição indevida de informações no front-end.

Controle: Na versão melhorada, as senhas foram substituídas por codificação Base64 (btoa) — apenas para fins didáticos, representando o conceito de "não armazenar em texto puro". Em produção, senhas devem ser armazenadas no servidor com hash bcrypt e jamais chegar ao front-end.

Limitação: A solução continua sendo front-end. Base64 não é criptografia — é apenas uma codificação. A solução real depende de back-end.

Item 2 — Campo senha type="text"

Problema: O campo de senha estava com type="text", exibindo a senha em texto visível durante a digitação.

Risco: Confidencialidade — exposição por observação direta (shoulder surfing).

Controle implementado: Alterado para type="password". Correção simples e efetiva no front-end.

Item 3 — Autenticação no front-end

Problema: A verificação de credenciais ocorre inteiramente no JavaScript. Um usuário pode abrir o console e executar usuarioAtual = usuarios[0] para se autenticar como admin sem saber a senha.

Risco: Violação de autenticidade. Qualquer regra de acesso é contornável.

Controle: Autenticação real exige servidor que receba credenciais, valide contra banco de dados e retorne token (ex: JWT). Impossível de resolver apenas no front-end.

Item 4 — Ausência de controle de sessão

Problema: Após login, o sistema não expira a sessão. Em dispositivos compartilhados, outro usuário pode acessar os dados do anterior.

Risco: Controle de acesso, confidencialidade.

Controle implementado: Timeout de 10 minutos simulado via setTimeout. Em produção, o controle de sessão deve ocorrer no servidor com tokens com tempo de expiração.

Item 5 — Controle de acesso por perfil (RBAC)

Problema: Todos os perfis acessavam todas as funcionalidades indistintamente.

Risco: Confidencialidade, integridade, violação do princípio do menor privilégio.

Controle implementado: Objeto centralizado PERMISSOES mapeia cada perfil às suas permissões. Todas as funções verificam temPermissao() antes de executar. Menu desabilita botões sem acesso. Conceito: RBAC (Role-Based Access Control).

Limitação: Verificação ocorre no front-end e pode ser contornada via console. Em produção, o servidor deve validar permissões em cada requisição.

Item 6 — Aluno vê ocorrências de todos

Problema: A função de renderização exibia todas as ocorrências sem filtro por perfil.

Risco: Confidencialidade, violação da LGPD (acesso a dados pessoais de terceiros sem necessidade).

Controle implementado: Filtro por matrícula: alunos veem apenas ocorrências onde matricula === usuarioAtual.matricula. Princípio aplicado: menor privilégio e minimização de dados.

Itens 7, 8 e 9 — Exposição de CPF e senhas

Problema: CPF exibido completo, senhas visíveis na aba de usuários e incluídas na exportação JSON.

Risco: Confidencialidade crítica, violação da LGPD (dados pessoais sensíveis).

Controles implementados: CPF mascarado (***.***.***-XX); senhas removidas da renderização de usuários; exportação JSON restrita a ocorrências (sem array de usuários).

Itens 10 e 11 — Logs no localStorage e apagáveis por qualquer perfil

Problema: Logs armazenados localmente podem ser apagados pelo próprio usuário, eliminando a trilha de auditoria.

Risco: Rastreabilidade, integridade. Sem logs confiáveis, incidentes não podem ser investigados.

Controle parcial: Ação de limpar logs restrita ao perfil admin, com confirmação obrigatória. Um log da própria limpeza é registrado antes. A solução definitiva depende de back-end com logs persistentes e imutáveis.

Item 16 — Proteção contra XSS

Problema: Conteúdos digitados pelo usuário eram inseridos diretamente no innerHTML sem sanitização, permitindo injeção de HTML e scripts (Cross-Site Scripting).

Risco: Integridade, possível roubo de dados via script malicioso.

Controle implementado: Função escHTML() que usa document.createElement + textContent para escapar todo conteúdo antes de inserir no DOM.

11. Limitações da Solução Entregue

Mesmo após as melhorias implementadas, as seguintes limitações permanecem:
  • Autenticação simulada: qualquer usuário com conhecimento de JavaScript pode contornar o login via console do navegador;
  • Sem banco de dados: dados ficam no localStorage, sem integridade, sem backup e limitados ao navegador de cada usuário;
  • Logs não confiáveis: mesmo restritos a admin, os logs podem ser manipulados diretamente no localStorage via DevTools;
  • Controle de acesso contornável: as verificações de perfil estão no JavaScript e podem ser neutralizadas no console;
  • Senhas "codificadas" (btoa) não são seguras: Base64 é reversível trivialmente; a melhoria é apenas conceitual;
  • Sem HTTPS garantido: em servidor local, dados trafegam sem criptografia;
  • Sem proteção contra força bruta: não há limitação de tentativas de login.

12. Conclusão

O sistema, da forma como foi recebido originalmente, poderia ser usado em produção com dados reais?

Não. O sistema, em sua versão original, não reúne condições mínimas de segurança para uso com dados reais de alunos e funcionários.

Os problemas identificados comprometem todos os pilares fundamentais da Segurança da Informação:

  • Confidencialidade: senhas em texto puro, CPF exposto, qualquer aluno vê dados de colegas, exportação com credenciais;
  • Integridade: dados armazenados em localStorage podem ser alterados diretamente, logs apagáveis por qualquer perfil;
  • Disponibilidade: sem servidor e sem backup, dados podem ser perdidos definitivamente;
  • Autenticidade: autenticação contornável via console do navegador;
  • Rastreabilidade: logs não são confiáveis e podem ser adulterados ou destruídos;
  • LGPD: CPF coletado e exposto sem necessidade, sem controle de acesso adequado, sem responsável técnico pelo dado.

A versão melhorada entregue neste trabalho representa avanços relevantes dentro das limitações do escopo front-end: controle de acesso por perfil (RBAC), mascaramento de CPF, proteção contra XSS, timeout de sessão simulado, validação de dados e minimização de dados nos logs e exportações. Contudo, essas melhorias têm caráter parcial e didático.

Para que o sistema pudesse ser considerado apto para uso em produção, seriam necessários, no mínimo:

  • Desenvolvimento de back-end com autenticação real (ex: Node.js, Java, Python) e tokens JWT;
  • Banco de dados relacional protegido (PostgreSQL, MySQL) com controle de acesso;
  • Armazenamento de senhas com hash bcrypt no servidor;
  • Logs persistentes e imutáveis no servidor;
  • HTTPS com certificado TLS válido;
  • Política de privacidade e termos de uso em conformidade com a LGPD;
  • Processo formal de revisão de segurança (pentest ou code review) antes do go-live.
